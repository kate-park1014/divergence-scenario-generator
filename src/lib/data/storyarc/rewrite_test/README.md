# storyarc 재작업 (rewrite_test)

기존 storyarc 를 Gemini 로 다시 써서 **단순하고, 1~5화가 이어지고, 보스마다 개성 있는** 이야기로 만든다.
원본은 그대로 두고 이 폴더에 새 파일로 저장한다.

- 이 폴더의 `storyarc_<id>.ts` : 재작업 결과 (다시 돌리면 덮어씀)
- 이 폴더의 `storyarc_<id>.judge.json` : 채점 결과 (다시 돌리면 덮어씀)
- 이 README 는 덮어쓰지 않음

## 실행

```bash
npm run dev &                                              # dev 서버 (포트 5178)

npm run rewrite:storyarc -- --id=modern_evannext_1        # 1개
npm run rewrite:storyarc -- --id=a,b,c --concurrency=5      # 여러 개
npm run rewrite:storyarc -- --id=a --judge-only             # 다시 쓰지 않고 채점만
npm run rewrite:storyarc -- --id=a --no-judge               # 채점 없이 다시 쓰기만
```

- id 는 `src/lib/data/storyarc/index.ts` 에 등록된 storyarc 여야 한다
- 비용: storyarc 1개당 Gemini(2.5 flash) 2~5번 호출. 10개에 5분쯤

## 흐름

```
npm run rewrite:storyarc            scripts/rewrite-storyarc.mjs
        ▼
POST /api/storyarc/rewrite          src/routes/api/storyarc/rewrite/+server.ts
  ① 준비: 원본 찾기 · 장르 배정 · 이 폴더의 다른 재작업본에서 이미 쓴 소재 모으기
  ② storyarc 마다 (동시 실행)
     프롬프트 만들기          src/lib/prompts/storyarcGen.ts (buildStoryarcRewritePrompt)
     → Gemini 다시 쓰기       (story_spine 요약을 먼저 쓰고 나머지를 맞춤)
     → 코드 검사              걸리면 오류 + 이전 출력을 붙여 다시 요청 (최대 3번)
     → 필수 필드 빠지면 저장 안 함 (실패)
     → 고정값 덮어쓰기 → 저장 → 소재 목록에 등록
     → Gemini 채점            src/lib/prompts/storyarcJudge.ts (측정만, 다시 쓰기 안 함)
  ③ 러너가 결과 출력
```

### 고정값 (Gemini 가 바꿔도 코드가 덮어씀)
id, level, theme, rising_count, final_boss 의 id·name·외형(appearance_npc/boss)·zodiac_sign, NPC 키 목록, 화별 act·boss, tension 1/3/5

### 새로 생기는 필드
| 필드 | 뜻 |
|---|---|
| `genre` | 배정된 장르 (id 로 고정, 같은 묶음 안에서는 겹치지 않음) |
| `stage` | 무대: 보스가 있는 한 장소 |
| `story_spine` | 화별 1~3문장 줄거리 요약 (5화에 결말). 화별 `protagonist_action`(그 화 행동), `lesson`(2~4화: 앞 화에서 배운 것), `hidden_link`(1~4화: 그 행동이 사실은 왜 wrong_action 과 같은 일인지, 5화에 드러남) |
| `key_object` | 1~5화에 계속 나오는 핵심 물건 (누구나 아는 일상 물건) |
| `world.how` | 왜 나쁜 결과가 생기는지: 핵심 물건이 어떻게 작동하는지 한 문장 |
| `final_boss.want` | 보스가 이 일로 얻는 구체적인 이득 한 문장 |
| `wrong_action` / `right_action` | 1~4화 행동이 사실은 모두 하는 일(1화에는 그대로 함) / 5화 정답 행동 (서로 반대) |
| `scenarioOutline[].place` | 그 화의 장소: 무대 안의 한 구역 (다섯 화 모두 다름) |
| `scenarioOutline[].random_boss_title` | 1~4화 그 화 일반 보스의 직업 (화마다 다른 사람·다른 직업, 무대에 있을 법한 사람). 5화에는 없음 |
| `boss_name_korean` | 보스 한국어 이름. 최종보스는 호칭(직업) 없이 이 이름으로만 부른다 (호칭은 NPC·일반 보스만) |
| `boss_trace` | 1화에 보스가 드러나는 매체 (예: 스피커 방송, 화면 문구) |
| `scenarioOutline[].boss_trace` | 1~4화 그 화의 흔적. 화마다 다른 매체 (주인공이 같은 존재인 줄 모르게). 그 화 summary 에 그대로 나옴 |
| `npc_roles.<key>.title` | NPC 호칭 |
| `npc_roles.<key>.turn_order` / `turn_scene` | 마음을 바꾸는 화와 이유 장면 (아크당 1명까지) |

### 이야기 규칙 (프롬프트)
- **이어지는 이야기**: 1화에 주인공이 wrong_action 을 하고 결과를 겪으며 "그건 하면 안 된다"를 배운다. 2~4화는 앞 화 피해에서 출발하고, 주인공은 앞 화 행동을 다시 하지 않는다. 대신 핵심 물건과 상관없어 보이는 다른 물건·장치를 다루는데, 그 안에 핵심 물건이 숨어 있어 결국 같은 일(wrong_action)이 된다(`hidden_link`). 5화에 그 연결과 보스가 드러난다. 매화 같은 행동을 반복하면 "기억을 잃은 히어로"가 되어서 이렇게 바꿈
- 보스는 1~4화에 **얼굴 없이 흔적(그 화 boss_trace: 목소리·글자·물건, 화마다 다름)으로만** 나와 그 화 행동을 권하고, 5화에 처음 모습을 드러내며 정답 행동을 막다가 무너진다 (보스 평상시 모습 이미지가 없어서 이렇게 정함)
- 주인공은 1~4화마다 그 화 행동을 직접 하고 그 결과(world.rule 과 같은 종류의 피해)를 겪는다. 5화에 정답 행동을 한다
- 주인공 = 플레이어 = 히어로라 **속는 사람**이지 고집부리는 사람이 아니다: 1~4화 틀린 행동은 선한 이유(사람 돕기·부탁·위기)로 하고 당장은 효과를 본 뒤 대가가 드러난다. 보스 흔적의 말은 친절한 해결책처럼 들린다. 1~4화에 틀린 행동을 경고하는 건 warn 일반 보스뿐(NPC 는 하기 전에 말리지 않음, 결과를 보고 의심은 됨). 채점 J16
- 1~4화 일반 보스의 편은 화마다 코드가 id 로 고정(`bossSidesForId`, 다시 돌려도 같음, 스토리마다 조합이 다름) → `scenarioOutline[].random_boss_side`
- 1~4화 속는 방식도 코드가 id 로 고정(`deceiveModesForId`) → `scenarioOutline[].deceive_mode`. 1화 `direct`(직접 속음), 2~4화는 후보 9개(`DECEIVE_MODE_POOL`) 중 서로 다른 셋: `verify`(확인했는데 확인 수단이 흔적) / `npc_acts`(주인공은 멈추자는데 주 NPC 가 먼저 해 버려 함께 마무리) / `avoid`(비슷한 일을 피하려는데 흔적이 경고처럼 다른 길을 권함) / `pressure`(수상하지만 사람이 위험해 시간이 없음) / `undo`(앞 화 피해를 되돌리려는 방법이 그 화 행동) / `tradeoff`(흔적이 작은 대가를 솔직히 말하고, 주인공이 감수하지만 진짜 대가는 훨씬 큼) / `bait`(흔적이 꾸민 가짜 위기를 막으려다 함) / `piecemeal`(작은 단계로 나눠 하는데 합치면 그 화 행동) / `gift`(흔적에게 먼저 진짜 도움을 받고, 다른 사람을 위한 부탁처럼 들어줌). 방식 설명은 `DECEIVE_MODE_LABEL` 한 곳에 두고, 그 아크에 뽑힌 방식만 프롬프트 USER "화별 속는 방식"과 채점 J18 에 넣음 (시나리오 프롬프트는 chapterGenRewrite.ts 의 `modeScene`). 매화 "곤란한 NPC → 흔적의 해결책 → 이번엔 다르다 → 행동" 같은 순서가 반복돼서 넣음. lesson 은 "이번엔 어떻게 조심하는지". 코드 검사: npc_acts 화 summary 에 주 NPC 이름. 시나리오 프롬프트도 그 화 방식대로 장면을 씀
  - `warn` 경고하는 쪽(최종보스 편 아님): 주인공의 틀린 행동을 막아서며 경고하고, 경고는 맞다. 막는 까닭이 자기 사정처럼 보여 주인공은 믿지 않는다(그 이유가 summary 에 나옴). 5화에 그 경고가 맞았음을 깨달을 수 있다
  - `ally` 최종보스 편: 주인공의 의심·이탈·전진을 막고, 틀린 행동은 말리지 않는다
  - 어느 편이든 정답 행동은 말하지 않는다. 필드가 없는 예전 storyarc 는 ally 로 본다
- 규칙(world.rule)은 한 문장: "[틀린 행동]을 하면 [무대에서 눈에 보이는 나쁜 결과]가 일어난다"
- NPC 는 이유 장면이 있으면 마음을 바꿔도 된다. 1~4화에 보스 단서·목적·정체가 드러나도 된다
- 2~4화 summary 는 앞 화가 남긴 피해에서 출발해도 된다. 2~4화에 새 미스터리는 하나만
- 1~4화는 화마다 행동·장소·이유·대가·흔적이 다르다 (2~4화 요약 유사도 0.5 이상이면 다시 쓰기, 채점 J14)
- 프롬프트 예시는 소재 없는 틀(`[...]`)만 쓴다. 구체적인 예시를 넣으면 Gemini 가 그대로 베낀다

### 코드 검사 (어기면 다시 요청)
| 묶음 | 검사 |
|---|---|
| 구조 | 씬 5개, 복선 4개, 방 번호 1·3·5·9·15, 복선 위치 중복, NPC 키, 요약 1~5화 |
| 행동 | 1화=wrong_action·5화=right_action 그대로, 2~4화 행동은 핵심 물건 이름 없음·wrong/right·앞 화와 동사가 다르고 비슷한 뜻(`SIMILAR_VERBS`)도 아님, "~한다" 꼴, lesson(2~4화)·hidden_link(1~4화, 2~4화는 핵심 물건 포함) 있음, wrong/right 가 비슷한 동사 아님, "~않는다" 아님 |
| 핵심 물건·규칙 | 핵심 물건이 1~5화 summary 에 있음, 규칙은 한 문장 + 핵심 물건 + "도시"·"~않으면" 없음 |
| 인물 | 보스가 1~4화에 그 화 boss_trace 로 나옴(화마다 다른 매체, 얼굴·몸이 보이는 표현 금지, 보스 말에 정답 동사 금지), 보스 한국어 이름 첫소리, 호칭 겹침(NPC·1~4화 일반 보스 직업, 같은 낱말 또는 앞 두 글자가 같은 낱말), 마음 바꾸는 NPC 1명 + 그 화에 NPC 이름과 이유 장면 핵심 낱말 2개 |
| 일반 보스 | 1~4화마다 직업이 있고 그 화 summary 에 나옴, 막는 동사 필수, warn 화는 핵심 물건이 문장에 나옴 / ally 화는 핵심 물건에 대한 행동을 막지 않음 (직업 이름 속 낱말은 빼고 봄), 보스 이름·사연·설득·정답 행동 금지 |
| 5화 | 보스가 정답 행동을 막음, 무너지는 장면, 보스가 정답을 반기지 않음 |
| 글쓰기 | 흐린 말, 마크다운, "(복선: …)" 메모, 영어 보스 이름, 소문형 복선, summary·story_spine 에 "보스" 게임 용어 없음 ("암시장"의 "암시"는 흐린 말로 안 봄) |
| 개성 | 핵심 물건이 일상 물건(만질 수 없는 낱말 `ABSTRACT_OBJECT` 없음, 꾸밈말 두 낱말까지), world.how 한 문장 + 핵심 물건, final_boss.want 있음 + 광기·혼란 같은 말 없음, 무대에 "도시" 없음, 다른 재작업본과 핵심 물건·무대가 겹치지 않음("조각" 같은 흔한 끝말은 앞 낱말까지 비교) |

### 채점 (Gemini, 코드로 못 보는 것)
J1 인물 편 유지 · J2 정답 행동 실패 장면 없음 · J3 결말이 장면 · J4 화당 새 미스터리 하나 · J5 앞 화를 이어받음 · J6 5화 보스가 정답에 맞섬 · J7 규칙과 정답 일치 · J8 인물 구분 · J9 일반 보스 매화 다름 · J10 예시 베끼기 없음 · J11 장르 · J12 두 행동이 반대 · J13 1~4화 보스는 흔적으로만 · J14 화마다 다른 상황 · J15 경고를 무시하는 이유 · J16 주인공에게 공감 · J17 숨은 연결이 그럴듯함 · J18 화마다 속는 방식이 다름

불통과면 근거 문장을 원문 그대로 인용하고, 그 인용이 원문에 있는지 코드로 대조한다(`quote_found`). Gemini 가 쓰고 Gemini 가 채점하므로 판정이 흔들릴 수 있다. 문제 위치를 찾는 용도로 본다.

## 결과 읽는 법
- `✓` 저장 성공 / `✗` 실패 (저장 안 함, 이전 결과가 남아 있음)
- `[남은 오류]` 3번 다시 써도 남은 코드 검사 오류
- `[채점 ✗ J?]` 불통과 항목과 근거 문장. `(인용이 원문에 없음)` 이면 채점이 근거를 지어낸 것
- 맨 끝 `[채점 요약]` 항목별 통과 수

## 테스트·개선 방법
1. 같은 묶음을 다시 돌리기 전에 이 폴더를 백업한다
2. 실행해서 `[채점 요약]` 과 `[남은 오류]` 수를 본다
3. 자주 나오는 문제를 규칙(storyarcGen.ts)이나 코드 검사(rewrite/+server.ts)로 옮긴다
4. 다시 돌려 이전과 비교한다

## 주의
- 이 폴더 파일은 `index.ts` 에 등록되지 않는다 (id 가 원본과 같음). 시나리오 생성(bulk-pipeline)은 아직 이 결과를 읽지 못한다. 쓰려면 원본 파일에 덮어쓰거나 등록 방식을 정해야 한다
- 새 필드(story_spine, key_object 등)는 chapterGen 이 아직 읽지 않는다
- 1~4화의 보스 대사는 얼굴이 없으므로, 시나리오(chapterGen)에서는 narrator 지문이나 NPC 가 전하는 말로 써야 한다 (chapterGen 아직 미반영)

# 시나리오 만들기 (재작업 storyarc → 대사)

이 폴더의 storyarc 로 시나리오(5화 × 방 5개 대사)를 만든다. 기존 시나리오 파이프라인(bulk-pipeline)과 섞이지 않게 **생성만** 하고 별도 폴더에 저장한다 (번역·output 저장 없음).

```bash
npm run gen:rewrite-scenarios -- --id=modern_evannext_1            # 1~5화
npm run gen:rewrite-scenarios -- --id=modern_evannext_1 --orders=1,5
npm run gen:rewrite-scenarios -- --id=a,b --concurrency=2
```

- 결과: `output_list/rewrite_test/<id>/`
  - `script.md` 1~5화 읽기용 대본 (가장 보기 편함) / `script_0N.md` 화별
  - `scenario_0N.json` 게임 데이터 형식 (actors 에 대사에 나온 NPC 포함, 각 NPC 에 직업 `role: { korean }` — storyarc `npc_roles.<key>.title` 에서. 1~4화는 `boss.role: { korean }` 에 그 화 일반 보스 직업)
- 프롬프트: `src/lib/prompts/chapterGenRewrite.ts` (게임 데이터 형식 규칙만 `chapterRules.ts` 에서 공유)
- 엔드포인트: `src/routes/api/scenario/rewrite-test/+server.ts`, 러너: `scripts/gen-rewrite-scenarios.mjs`
- 비용: 화당 Gemini 1~3번 (5화 동시)

### 프롬프트 원칙
- storyarc 필드는 "무슨 일이 일어나는지" 메모로 주고, 대사는 자연스러운 말로 쓰게 한다 (필드 문구·"이번 화"·대괄호를 대사에 옮기지 않게)
- 방 배치는 꼭 필요한 장면만 고정: 방 1 첫 줄 narrator 상황 한 줄 / 방 1~9 에 보스 흔적·주 NPC·새 의문·주인공의 행동과 결과 (순서 자유) / 방 15 전투
- 1~4화 최종보스는 boss_trace 로만 (narrator 지문 속 따옴표 또는 NPC 가 전함). 5화 방 15 에서 처음 모습 (speaker 'boss')
- 최종보스 이름은 1~4화에 쓰지 않는다(흔적으로만 부름, 코드 검사). 5화에는 NPC 가 전하거나 흔적에 이름이 뜨는 장면으로 소개한 뒤에만 쓰고, 파티 대사·prologue 가 먼저 쓰지 않는다. (예전에는 1화에 소개 장면을 넣었는데, 근거 없이 이름을 아는 대사가 생겨서 뺌)
- 1~4화는 줄거리 요약에서 5화를 숨긴다. 2~4화 단서는 화마다 나눠 준다
- 출력 예시를 넣지 않는다 (예시 문장을 베낀다). 형식은 출력 스키마가 강제
- 일반 보스는 방 15 밖에서는 방 하나에만 나온다. warn 이면 틀린 행동 전에 한 번만 경고하고, 파티는 경고를 비웃지 않고 왜 도와야 하는지 말한다. 틀린 행동과 이어지는 이상 징후 단서는 행동 뒤에 (storyarc 복선 규칙도 같음). 그 화 `random_boss_side` 대로: warn 이면 틀린 행동을 막으며 경고하고 파티는 믿지 않는 이유를 대사로 말함 / ally 면 의심·전진을 막고 틀린 행동은 말리지 않음. 정답 행동은 말하지 않는다
- 주인공이 경고를 듣고도 틀린 행동을 하면 왜 그게 해결책이라 믿는지 대사로 말한다. NPC 는 앞에서 한 말과 같은 입장에서 반응한다 (부추긴 NPC 가 갑자기 탓하지 않음)
- direction 의 focus 는 쓰지 않는다 (프롬프트로 막고, 남으면 저장 전에 지움)
- 화별 행동·흔적은 `arcEpisode.ts`(`actionOf`·`traceOf`·`lessonOf`·`hiddenLinkOf`)로 읽는다. 예전 storyarc(화별 필드 없음)는 아크 하나짜리 값으로 대신한다
- 2~4화(이어지는 storyarc 만): 방 1~3 에 앞 화 피해와 배운 것을 한 줄로 떠올리고, 이번 행동이 왜 다르다고 믿는지 말한다. 파티는 그 화 행동이 나쁜 결과를 낳은 것은 알아도 되지만, 흔적들이 같은 존재라는 것·행동들이 사실 같은 일이라는 것은 모른다. `hidden_link` 는 5화에만 넘긴다(앞 화 대사에 새어 나오지 않게)
- 5화: 1~4화 행동의 숨은 연결을 깨닫는 장면 → 정답 행동
- 검토 R10 "앞 화와 어긋남": 앞 화 행동·흔적을 다시 믿음, 같은 깨달음 반복, 1~4화에 숨은 연결을 짐작함

### 검토자·수정자 (기본 켜짐, `--no-review` 로 끔)
생성과 코드 검사가 끝난 뒤 1번만 돌림. 프롬프트: `src/lib/prompts/scenarioReview.ts`
1. 검토자: 1~5화 대본 전체를 한 번에 읽고(temperature 0) 정해진 항목 R1~R9 에 어긋나는 줄만 주소·원문 인용과 함께 찾음 — R1 보스 이름 소개 · R2 질문에 답 · R3 앞뒤 이어짐 · R4 NPC 입장 · R5 주인공 공감 · R6 파티 대사는 한 사람이 말해도 되게(이어지는 파티 대사 말투, 파티원끼리 말 걸기·제안, 앞 파티 줄에 반응) · R7 게임 용어 · R8 일반 보스 편 · R9 5화 경고 회수
2. 수정자: 문제가 있는 화만, 그 줄만 줄 단위로 고침 (바꾸기·지우기·뒤에 넣기). 다시 생성해도 남은 코드 검사 오류도 함께 넘김. 고친 뒤 코드 검사에 새 오류가 생기면 그 오류를 알려 주고 원본에서 1번 더 고침, 그래도 생기면 그 화는 원래대로 둠
3. 확인: 처음 찾은 문제가 풀렸는지 + 고친 줄이 새 문제를 만들었는지만 봄 (전체를 다시 검토하면 실행마다 기준이 흔들려 비교가 안 돼서)
- 결과: `<id>/review/` — script_before.md(고치기 전), review.json, edits_0N.json, verify.json
- `--review-only`: 다시 생성하지 않고 기존 scenario_0N.json 에 검토·수정만
- 비용: 스토리당 검토 1 + 문제 있는 화마다 수정 1 + 확인 1
